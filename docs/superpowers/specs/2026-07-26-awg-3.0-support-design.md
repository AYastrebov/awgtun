# AWG 3.0 Support — Design

Date: 2026-07-26
Status: Approved
Reference implementation: [amneziawg-go](https://github.com/amnezia-vpn/amneziawg-go) @ `9f5d948bc72cc554791cfe0fb91527e4acfb6b79` (all 3.0 behavior is in commit `457d920` "feat: amneziawg 3.0")

## Background

This boringtun fork implements AmneziaWG 2.0: dynamic message headers (H1–H4), crypto padding (S1–S4), junk packets (Jc/Jmin/Jmax), and custom signature packets (I1–I5). The 2.0 code lives almost entirely in `boringtun/src/amnezia.rs` plus `Tunn`-level plumbing in `boringtun/src/noise/mod.rs`; the Noise core only gained a `msg_type: u32` parameter. Exposed surfaces: Rust `Tunn` API and C FFI. The device/UAPI/CLI path is standard WireGuard only.

AWG 3.0 adds three features on top of 2.0:

1. **Header protection** — fast (unauthenticated) encryption of low-entropy header fields.
2. **Content padding** (`ContentPaddingAddition`) — random extra padding inside the AEAD envelope of transport packets.
3. **Randomized timings** — WG timing constants become per-use random picks from configured ranges.

There is no wire-level version negotiation: behavior is entirely config-driven. Default (all-zero) config remains byte-identical to stock WireGuard.

## Goals

- Full 3.0 parity with amneziawg-go @ `9f5d948` for the three features above.
- Exposed on the same surfaces as 2.0: Rust `Tunn` API + C FFI. No device/UAPI/CLI wiring.
- No breakage of the existing 2.0 API (`Amnezia2Config`, `Tunn::new_with_amnezia`, `amnezia_config`).

## Non-goals

- Server-side/device-mode AWG deployment (same limitation as 2.0).
- Live interop test suite against amneziawg-go (same limitation as 2.0; noted in AMNEZIA.md).
- Randomizing `RekeyAfterMessages` / `RejectAfterMessages` (upstream does not randomize these).

## Configuration (`boringtun/src/amnezia.rs`)

### New types

- `U32Range { lo: u32, hi: u32 }` — generic inclusive range with `pick(&mut dyn RandomSource) -> u32`, `lo()`, `hi()`, parse from `"a"` / `"a-b"`. Used for content padding and timing ranges. (`HeaderRange` stays as-is for headers; refactoring it onto `U32Range` is allowed if it doesn't change its public API.)
- `TimingRanges` — optional ranges (each `Option<U32Range>` or a range that is "unset" when zero) for:
  - `rekey_after_time` (default 120 s)
  - `rekey_timeout` (default 5 s)
  - `reject_after_time` (default 180 s)
  - `keepalive_timeout` (default 10 s)
  - `max_handshake_attempts` (default 18)
  - `persistent_keepalive` (default 0 = off)
- `Amnezia3Config` — aggregate reusing the 2.0 blocks (`HeaderConfig`, `PaddingConfig`, `JunkConfig`, `InitPacketConfig`) plus:
  - `header_protection_key: Option<[u8; 32]>` (`None` = feature off)
  - `content_padding_addition: Option<U32Range>`
  - `timing_ranges: TimingRanges`
  - `mtu: u32` (default 1420, matching Go's default device MTU; used only for content-padding clamping)

### Validation

- When `header_protection_key` is set: **S1–S4 must all be ≥ 12** (`HeaderCipherNonceSize`). Note: the upstream README says "8 at least", but the code (`uapi.go:822-829`) enforces ≥ 12. We follow the code.
- All ranges: `hi >= lo`. A fully-zero range means "unset → WG default".
- All 2.0 validation (header overlap, reserved 1–4, padding/junk limits, CPS rules) applies unchanged.

## Header protection

### Primitive

- Raw **ChaCha20** stream cipher (unauthenticated, XOR only), 32-byte key, 12-byte nonce, block counter 0 — equivalent to Go's `chacha20.NewUnauthenticatedCipher`.
- Implementation via the RustCrypto `chacha20` crate (`XORKeyStream` equivalent: `cipher.apply_keystream(buf)`), since `ring` does not expose a raw ChaCha20 keystream API.

### Nonce derivation

Every AWG packet already starts with a random crypto-padding prefix (S1–S4 bytes). The **first 12 bytes of the datagram** (i.e. of the random prefix) are the ChaCha20 nonce. This is why S1–S4 ≥ 12 is required.

### Send path (Tunn level, `boringtun/src/noise/mod.rs`)

After a message has been fully formatted at `dst[padding..]` — including MAC1/MAC2 for handshake packets — and the random prefix has been written at `dst[..padding]`:

1. Build the cipher with `nonce = dst[0..12]`.
2. XOR in place:
   - handshake initiation: 148 bytes
   - handshake response: 92 bytes
   - cookie reply: 64 bytes
   - transport: **first 16 bytes only** (type, receiver index, counter); the AEAD ciphertext is untouched.

Order matters: MACs are computed over the plaintext message first, then the message (MACs included) is encrypted. On the wire, mac1/mac2 are hidden from DPI.

### Receive path (Tunn level)

Extend `determine_padding` (`noise/mod.rs:683`) and its callers:

1. For each candidate (padding, range, expected size): nonce = `src[0..12]`; decrypt the 4 type bytes as `src[padding..padding+4] ^ keystream[0..4]`; test membership in the corresponding `HeaderRange`. Size check as today (exact for handshake types, `>=` for transport).
2. On match, decrypt in place: the full message for handshake types, the first 16 bytes for transport. (Equivalent to upstream's continuous-keystream dance; XOR of the whole span with `keystream[0..N]` produces identical bytes.)
3. Hand the decrypted buffer to the **unmodified** Noise parse / MAC-check / cookie functions. The Noise core does not change.

I1–I5 signature packets and Jc junk packets are never header-protected (receiver drops them as unknown type/size, as today).

## Content padding (`ContentPaddingAddition`)

Transport messages only, keepalives included. In `Tunn::encapsulate`:

1. If CPA is set: `add = range.pick(rng)`, clamped to the remaining space in the last MTU segment — `size = packet_size % mtu` (when `packet_size > mtu`), `add = min(add, mtu - size)`. The classic pad-to-multiple-of-16 is **skipped entirely** when CPA is set (final sizes are intentionally not 16-aligned).
2. Append `add` zero bytes to the IP packet **before** AEAD seal, so the padding is authenticated and needs no length field.
3. Keepalives (empty payload) also get `add` zero bytes (clamped to `mtu`).

Receiver: unchanged. AEAD `Open` yields `ip_packet ‖ zeros`; the IP total-length field trims the zeros (as upstream relies on).

## Randomized timings (`boringtun/src/noise/timers.rs`)

`Timers` gains an optional `TimingRanges`. A **fresh** random value is picked at each use (per timer arm / per check), never cached per handshake. Replicate upstream's pick semantics exactly:

| WG constant (default) | Replacement | Pick rule |
|---|---|---|
| `RekeyTimeout` (5 s) retransmit timer | `rekey_timeout` | `pick()` + existing jitter |
| `RekeyTimeout` min spacing between initiations | `rekey_timeout` | **Lo** |
| `KeepaliveTimeout` (10 s) | `keepalive_timeout` | `pick()` |
| `KeepaliveTimeout + RekeyTimeout` new-handshake timer | keepalive + rekey | **Hi**(keepalive) + `pick()`(rekey) + jitter |
| `RekeyAfterTime` (120 s) initiator rekey | `rekey_after_time` | `pick()` |
| `RejectAfterTime - KeepaliveTimeout - RekeyTimeout` receiver rekey | reject/keepalive/rekey | `max(0, pick(reject) - Lo(keepalive) - Lo(rekey))` |
| `RejectAfterTime` (180 s) keypair expiry | `reject_after_time` | **Hi** |
| `MaxTimerHandshakes` (18) | `max_handshake_attempts` | `pick()` per handshake initiation |
| `PersistentKeepalive` | `persistent_keepalive` | fresh `pick()` on every re-arm; 0 = off |

Unset (zero) ranges fall back to the classic WG constants, preserving current behavior.

## API & FFI

- Rust: `Tunn::new_with_amnezia3(..., amnezia: Amnezia3Config) -> Result<Tunn, ConfigError>` in `noise/mod.rs`. `Tunn::new` and `Tunn::new_with_amnezia` unchanged.
- FFI (`boringtun/src/ffi/mod.rs`): new `#[repr(C)] amnezia3_config` (all 2.0 fields + `header_protection_key: *const u8` pointing to 32 bytes, NULL = off; `content_padding_min/max`; per-timer min/max pairs; `mtu`) and `new_tunnel_amnezia3(...)`.
- Add the missing declarations for both the 2.0 (`amnezia_config`, `new_tunnel_amnezia`, `wireguard_poll_outgoing_packet`) and 3.0 FFI entry points to `wireguard_ffi.h` — fixes the existing header gap.
- Dependency: add RustCrypto `chacha20` to `boringtun/Cargo.toml`.

## Error handling

- New `ConfigError` variants: `HeaderProtectionRequiresPadding` (S<x> < 12 with key set), invalid timing/CPA range (`hi < lo`), invalid header-protection key length (FFI: NULL-vs-32-bytes contract documented; Rust type makes it unrepresentable).
- Runtime behavior unchanged: undecryptable/unknown packets are silently dropped, exactly as 2.0 and upstream.

## Testing

- `amnezia.rs` unit tests (with the existing `DetRng`): `U32Range` parse/pick, `TimingRanges` validation, `Amnezia3Config` validation (S ≥ 12 rule, range rules), keystream round-trip (encrypt → decrypt yields original; known-answer vector for ChaCha20 nonce/counter usage), CPA size/clamp computation.
- `noise/mod.rs` integration-style tests with two `Tunn`s:
  - Full AWG 3.0 handshake round-trip (both directions) with header protection on, non-default H/S params — asserts headers on the wire are *not* the configured H values and MACs are not visible in plaintext form.
  - Transport with CPA: wire sizes reflect random addition, receiver decrypts to the original IP packet; keepalive-with-CPA case.
  - Header protection off + 3.0 config otherwise: interoperates with a 2.0-style `Tunn`.
  - Timing ranges: with a deterministic RNG, armed timers fall within configured ranges; zero range = WG constant.
- No live interop tests against amneziawg-go (documented limitation, same as 2.0).

## Key fidelity notes (from upstream source)

- ChaCha20 block counter starts at 0 for every packet; keystream is conceptually continuous from the type field onward.
- MACs computed on plaintext **before** header encryption; receiver fully decrypts the header before `CheckMAC1`.
- Transport: only the 16-byte header is XOR'd; CPA zeros live inside AEAD; receiver trims via IP length.
- Type identification order on receive: size match against `Sx + msg_size` (transport: `>=`), then `type ^ keystream[0..4] ∈ Hx`.
- Junk + I-packets + initiation are separate datagrams sent before the handshake (this fork already queues them; upstream batches them in one `SendBuffers` — behaviorally equivalent).
- README/code mismatch: header protection requires S1–S4 ≥ **12** in code, "8" in README. Follow the code.
- Known upstream quirk: with CPA set, keepalives are padded, so their wire size differs from the keepalive constant and upstream counts them as "data sent" (arming the new-handshake timer). We replicate upstream behavior and do not special-case keepalives; this is documented in AMNEZIA.md.
